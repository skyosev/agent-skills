# Smell Hunter — TypeScript reference

Contents: Applicability of conditional categories · Generated-code eligibility · Per-category TypeScript content · Framework carve-outs · Idiom calibration · Phase 2 — smell scans · Phase 5 — TypeScript-specific evaluation

## Applicability of conditional categories

| Category | Applicable | Reason |
| -------- | ---------- | ------ |
| Primitive Obsession | **yes** | owned here as domain modeling, aliases included (brand-or-withdraw); type-hunter's Alias vs Named Type Mechanics is n/a in TypeScript, and its Enum Construct Mechanics needs an existing `enum` |
| God Module | **yes** | solid-hunter claims the class unit only (Responsibility Sprawl) — nothing in the party claims a file accumulating unrelated responsibilities |
| Mutable Global State | **yes** | module-level `let` and stateful singletons |
| Anemic Domain Model | **yes** | entity/service split is common in TypeScript backends |
| Class Abuse | **yes** | classes standing in for modules and functions |

**No language-only categories.** The construct of an existing `enum` belongs to type-hunter (Enum Construct
Mechanics); callback pyramids and unflattened promise chains belong to simplicity-hunter's Complex Control Flow.

## Generated-code eligibility

A file is generated (ineligible for reporting) only when identified by an authoritative in-file marker. No TypeScript-wide marker is defined; common ones are `// @generated`,
`/* eslint-disable */ // Code generated by …`, and the headers emitted by GraphQL Code Generator, Prisma, and
`protoc-gen-ts`. When a project documents its own, apply that. Scan globs such as `*.generated.*` / `__generated__/**`
/ `*.g.ts` / `generated/**` approximate it.

Vendored and build trees (`node_modules/`, `dist/`, `build/`, `.next/`), lockfiles, and Markdown-only inputs are also
ineligible.

## Per-category TypeScript content

### Data Clumps — TypeScript remedies

Extract a named `interface` or `type`. Signature-only clumps become a parameter object type; clumps recurring across
type definitions become a shared type used by intersection (`&`) or composition. React components with 4+ props that
travel together across components are the same finding — extract the prop group into a named type.

### Primitive Obsession — TypeScript remedies

Branded types for identity distinctions:

```typescript
type UserId = string & { readonly __brand: unique symbol };
type Email = string & { readonly __brand: unique symbol };
```

String-literal unions for status values (`type Status = 'active' | 'inactive' | 'suspended'`) instead of raw string
comparison; a dedicated money representation (integer minor units, or a decimal library already present) instead of
`number`; branded or unit-suffixed duration types instead of a bare `number`; a schema library already in the project
narrowing to the branded type at the boundary; template literal types for structured string domains — route paths
(`` `/api/${string}` ``), event names (`` `user:${string}` ``), design tokens — instead of plain `string`.
Over-engineered template-literal metaprogramming is type-hunter's Over-Powered Type Constructs.

**Structural typing voids alias-only remedies.** Two plain aliases (or interfaces) over the same field set stay
mutually assignable — "distinct named types" for same-shaped records buys zero compiler protection. Either the
remedy brands, or the finding must stand on something other than preventing mix-ups; if branding is not worth it,
withdraw rather than recommend a rename that enforces nothing.

**Closed-union facts: exhaustive `Record`, not `Set`.** For a per-member fact over a closed union, recommend
`Record<Union, T>` (with `satisfies` where useful) over `ReadonlySet` membership: a set makes a rename a compile
error but lets a new member join silently as absent/false; the exhaustive record forces a decision at every
addition.

### God Module — TypeScript signals

- `types.ts` joins the generic names (`utils`, `helpers`, `common`, `misc`) when its scope is unbounded
- A barrel `index.ts` that carries logic rather than re-exports, or that has become the project's import hub

**Action:** Keep barrels to re-exports.

### Mutable Global State — TypeScript markers

- Module-level `let` reassigned at runtime
- A module-level `const` holding a mutable container (`const cache = new Map()`) written to by multiple functions
- `class X { private static instance … static getInstance() }` holding state
- A module-level client, logger, or store replaced by a `setX()` function
- Globals hung off `globalThis` / `window`

Values built with `as const` are read-only tables (the read-only-table Not-a-finding).

**Singleton split (see SKILL.md).** TypeScript forms: a stateful `getInstance()` returning an object that holds data;
a stateless one is remedied by module-level named exports.

### Anemic Domain Model — TypeScript evidence

TypeScript forms of the required evidence:

- Transitions for one entity scattered across multiple services (`UserService.activate`, `BillingService.suspend`)
- External field mutation where the entity could own it — `order.status = 'shipped'` instead of `order.ship()`
- Tell-don't-ask at call sites: `if (order.status === 'paid') { … }` repeated across services instead of
  `order.canShip()`

TypeScript data carriers and data-plus-functions shapes (not findings): an `interface` plus functions operating on
it — TypeScript codebases legitimately model domains with plain data and functions; an API response type or ORM row
type with no behavior of its own.

### Class Abuse — TypeScript signals

- Class with only static methods (a namespace in disguise)

### Temporal Coupling — TypeScript remedies

Factory functions returning a fully initialized object; a builder whose type changes after each step so `build()` is
only callable once required fields are set; discriminated unions where each state variant exposes only its valid
transitions; dependencies accepted at construction rather than through setters. React hooks that depend on other
hooks having run first (beyond React's own rules) are the same smell.

### Comments as Deodorant — TypeScript signal

In addition to the shared signals: a JSDoc `@description` that narrates the implementation algorithm rather than
stating the public contract.

## Framework carve-outs

Exempt only the shape the named construct actually requires:

- **Angular `@Component`, `@Directive`, `@Pipe`; Nest `@Controller`, `@Module`** — these constructs are declared as
  classes; the framework provides no functional equivalent. Not Class Abuse findings.
- **TypeORM / MikroORM `@Entity`** — the decorator-based mapping requires a class. The *anemic* evaluation still
  applies to where transitions live.

Explicitly **not** carve-outs, because the framework supports alternatives:

- **Nest and Angular providers** — a stateless `@Injectable()` service class is conventional, not mandated: both
  support `useValue` and `useFactory`, and Angular adds `InjectionToken` while Nest adds symbol/string tokens. A
  stateless service class is evaluated normally.
- **React** — components are functions by default; a class component is not a mandated shape in new code.

## Idiom calibration

TypeScript's structural typing, union and discriminated-union types, `satisfies`, `as const`, and its module system
are strengths, not smells. A module of exported functions is the idiomatic unit of grouping — reaching for a class is
what needs justification. When the type system can enforce a constraint, using it in place of a runtime check or a
naming convention is the fix, not a smell. Calibrate to TypeScript conventions, not to patterns from Java, C#, or
Python.

## Phase 2 — smell scans

Test files are `*.test.*`, `*.spec.*`, `*.e2e.*`, and `__tests__/**`. Data Clumps and Mutable Global State scans run
on `$TS_PROD`, the list without test files, with `$TEST_OWNED_EXCLUDE` for codebase mode. A list of test files only becomes `/dev/null`, never empty.

```bash
TS_FILES=$(cat <run>/typescript.txt); [ -n "$TS_FILES" ] || exit 1  # STOP: empty restore
TS_PROD=$(printf '%s\n' $TS_FILES | grep -Ev '\.(test|spec|e2e)\.[^/]*$|(^|/)__tests__/'); TS_PROD=${TS_PROD:-/dev/null}
EXCLUDE='--glob !**/node_modules/** --glob !**/dist/** --glob !**/build/** --glob !**/.next/** --glob !**/*.generated.* --glob !**/__generated__/** --glob !**/*.g.ts --glob !**/generated/**'
TEST_OWNED_EXCLUDE="$EXCLUDE --glob !**/*.test.* --glob !**/*.spec.* --glob !**/*.e2e.* --glob !**/__tests__/**"

# Feature envy: chained property access across module boundaries
rg -nH --pcre2 '\b[a-z]\w+\.[a-z]\w+\.[a-z]\w+' --type ts $EXCLUDE -- $TS_FILES

# Data clumps: signatures with 3+ parameters, multi-line included — test setup belongs to test-hunter
rg -nHU --pcre2 'function\s+\w+\s*\((?:[^,)]*,){2,}[^)]*\)' --type ts $TEST_OWNED_EXCLUDE -- $TS_PROD
rg -nHU --pcre2 '(?:const|let)\s+\w+\s*=\s*(?:async\s+)?\((?:[^,)]*,){2,}[^)]*\)\s*(?:=>|:)' --type ts $TEST_OWNED_EXCLUDE -- $TS_PROD

# Primitive obsession: two bare string/number params in sequence, number money, raw status strings
rg -nH --pcre2 'function\s+\w+\s*\([^)]*:\s*string\s*,[^)]*:\s*string' --type ts $EXCLUDE -- $TS_FILES
rg -nH --pcre2 '(?i)(price|amount|money|cost|balance)\s*[?]?\s*:\s*number' --type ts $EXCLUDE -- $TS_FILES
rg -nH --pcre2 '\bstatus\s*===\s*[\x27"]' --type ts $EXCLUDE -- $TS_FILES

# Temporal coupling: init/setup/configure methods
rg -nH --pcre2 '\b(init|setup|configure|prepare)\s*\(' --type ts $EXCLUDE -- $TS_FILES

# God module: line counts over the ELIGIBLE subset only
rg --files --type ts $EXCLUDE -- $TS_FILES | while read -r f; do wc -l "$f"; done | sort -rn | head -20

# Class abuse candidates
rg -nH 'class\s+\w+' --type ts $EXCLUDE -- $TS_FILES
rg -nH --pcre2 '^\s*(private\s+|public\s+)?static\s+\w+\s*\(' --type ts $EXCLUDE -- $TS_FILES

# Mutable global state and stateful singletons — shared test state belongs to test-hunter
rg -nH 'getInstance\s*\(' --type ts $TEST_OWNED_EXCLUDE -- $TS_PROD
rg -nH --pcre2 '^(export\s+)?let\s+\w+' --type ts $TEST_OWNED_EXCLUDE -- $TS_PROD
rg -nH --pcre2 '^(export\s+)?const\s+\w+\s*=\s*new\s+(Map|Set|WeakMap)\b' --type ts $TEST_OWNED_EXCLUDE -- $TS_PROD
rg -nH 'globalThis\.\w+\s*=' --type ts $TEST_OWNED_EXCLUDE -- $TS_PROD

# Anemic domain model: entities to inspect against their services
rg -nH --pcre2 'class\s+\w+(Service|Manager|Handler)\b' --type ts $EXCLUDE -- $TS_FILES
rg -nH --pcre2 '^\s*(?!this\b)\w+\.(status|state)\s*=' --type ts $EXCLUDE -- $TS_FILES

# Temporary field: transient-looking properties
rg -nH --pcre2 '\b(temp|cached|last|pending)\w*\s*[?]?\s*:' --type ts $EXCLUDE -- $TS_FILES

# Comments as deodorant: comment blocks before code (inspect for "what" vs "why"). Written to a file, never
# truncated: read it in pages.
rg -nH -B1 -A1 '^\s*// ' --type ts $EXCLUDE -- $TS_FILES > <run>/comments-ts.txt; wc -l <run>/comments-ts.txt
```

## Phase 5 — TypeScript-specific evaluation

For each `class`:

- Does it hold state? Does it have more than one public method?
- Could it be a plain function, a closure, or a module of named exports?
- Is it a singleton — and is it stateful (→ Mutable Global State) or stateless (→ Class Abuse)?
- Is its shape mandated by a named framework construct (see carve-outs), or merely conventional?

For each module-level `let` or mutable container with a write after initialization:

- Is it reachable across requests or test cases, making state leak between them?

For each god-module candidate:

- Is the barrel file carrying logic rather than re-exports?
