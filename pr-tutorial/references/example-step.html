Handles and picks: two decisions that come before all code

  • New
  • Field

  • Intents

The tutorial uses a small product: a panel with a length in mm. The panel gets more fields in later steps: an extension that makes it longer, and a net length that the engine computes.

Before you write a rule or a component, two questions need an answer, because every part of the configurator touches a field:

  1. How does code refer to a field? The input box, the rules, the drawing, the price and the saved file all mention the length.
  2. What does the configurator store? The form shows many values. Some came from the user. The engine computed the others.

A spreadsheet is a good model. You type into some cells. The other cells hold formulas. A formula refers to a cell by its address, for example B2. When you save the file, you save what you typed, and the formulas compute the rest each time you open it. A handle is the address. A pick is what you typed.

Decision 1: a field is a handle

A handle is a small constant object: an id and a kind. You make it once and import it everywhere.

panel.tsyour product code
import { choiceField, numberField } from '@fenstra/configurator';

export const panel = {
    length: numberField('panel.length'),  // the id is spelled here, and only here
    extra: choiceField('panel.extra')     // an extension that makes the panel longer; step 5 gives it options
};
Output · what the handles are at run time
panel.length{ id: 'panel.length', kind: 'number' }
panel.extra{ id: 'panel.extra', kind: 'choice' }

Code reads a field in two places. A component reads a field to show it. A rule reads other fields to compute a value. A rule is a function that the engine calls, for example "the net length is the length minus 10 mm". The engine gives each rule one argument, the context, by convention named ctx. The context has two members:

packages/configurator/src/engine/fields.tslines 56–59 ↗
export interface Context<C> {
    readonly catalog: C;                       // the product data, for example the allowed lengths; C is its type
    get<T extends Json>(field: Field<T>): T;   // the current value of another field
}

// a rule: the engine calls it with ctx
const net = (ctx) => ctx.get(panel.length) - 10;

So ctx.get needs a way to name a field. Step 2 shows where a rule goes and when the engine calls it.

A handle holds no value and no rule. Why so little? Compare it with the two other usual ways to name a field:

The three ways in code

A and B are sketches. They are not in the configurator. The compiler errors come from tsc --strict. The output of B comes from a real run of the sketch.

A. A string

A string API has to return any JSON, because it cannot know which field you mean.

sketch · not in the codeStringContext.get(id: string): Json
// the rule for the net length
const net = (ctx) => ctx.get('panel.length') - 10;
// error TS2362: The left-hand side of an arithmetic operation must be of type 'any', 'number', 'bigint' or an enum type.

// so each reader adds a cast, and the compiler does not check the cast
const length = ctx.get('panel.length') as number;  // ok
const extra  = ctx.get('panel.extra') as number;   // compiles, but the value is an option id such as 'b-50'
const typo   = ctx.get('panel.lenght') as number;  // compiles, but no such field exists

// an input box repeats the same string
useField('panel.lenght');                          // a React hook (step 4); compiles, fails only when the page runs

Each string is a copy. When you rename a field, you must find every copy with a text search.

B. A live field object

This is how many form libraries work. Each field is an object that holds its value and its own rule.

sketch · not in the codepanel.ts
import catalog from './catalog.json';

class LiveNumberField {
    value: number;
    constructor(readonly id: string, readonly limits: { min: number; max: number; default: number }) {
        this.value = limits.default;
    }
    set(value: number): void { this.value = value; }
    get error(): string | undefined {
        return this.value > this.limits.max ? 'OUT_OF_RANGE' : undefined;
    }
}

export const panel = { length: new LiveNumberField('panel.length', catalog.length) };
sketch · not in the codeLengthInput.tsx
import { panel } from './panel.ts';  // brings the class, the rule and catalog.json into the input box

const length: number = panel.length.value;  // typed: good
panel.length.set(180);

The problem: the module holds one object, so it holds one value. The server checks saved files. Two checks run at the same time:

To fix this, you make new objects for each configuration, for example createPanel(catalog). But then the input box cannot import panel. Something must give it the correct object, and it needs a name to ask for it. That name is a handle.

C. A handle

This is what the configurator does.

panel.tsnames only
export const panel = {
    length: numberField('panel.length'),
    extra: choiceField('panel.extra')
};
Rules, an input box, the servererrors from tsc --strict
// the rule for the net length
const net = (ctx) => ctx.get(panel.length) - 10;   // a number, no cast
ctx.get(panel.extra) - 10
// error TS2362: The left-hand side of an arithmetic operation must be of type 'any', 'number', 'bigint' or an enum type.
ctx.get(panel.lenght)
// error TS2551: Property 'lenght' does not exist on type '{ length: NumberField; extra: ChoiceField<Option>; }'. Did you mean 'length'?

// an input box
import { panel } from './panel.ts';   // two small objects: no rule, no catalog
useField(panel.length);               // the store gives the value (step 4)

// the server: each check computes from its own picks; nothing is shared
resolve(definition, catalog, { 'panel.length': 180 });   // no issue (resolve: step 2)
resolve(definition, catalog, { 'panel.length': 250 });   // issue OUT_OF_RANGE

The handle keeps what B does well: a typed value and a compile error for a typo. It drops what goes wrong in B: the value and the rule. The rule goes to the product definition (step 2). The value goes to the store (step 3).

The handle also gives the type. TypeScript knows the result type of ctx.get(handle) from the handle:

What the compiler sayschecked with tsc --strict
const length: number = ctx.get(panel.length);   // ok
const extra: string  = ctx.get(panel.extra);    // ok: a choice holds an option id
const wrong: string  = ctx.get(panel.length);   // error TS2322: Type 'number' is not assignable to type 'string'.

Decision 2: store the picks, compute the rest

The engine calls a pick an intent: what the user wants. The type Intents is a record from field id to a JSON value. A field that the user did not touch has no entry.

The pickstype Intents
import type { Intents } from '@fenstra/configurator';

const typed: Intents = { 'panel.length': 180 };   // the user typed 180
const untouched: Intents = {};                    // the user typed nothing

Why not store the values that the form shows? Because a value cannot tell why it is there. Three cases show what the picks keep and the values lose. The tables are real engine output. The catalog is the product data from the server, for example the default length.

Case 1. The default changes. The catalog changes the default length from 150 to 160.

Output · same picks, two catalogs
PicksDefault 150Default 160
{}length 150 (default)length 160 (default): follows the catalog
{ 'panel.length': 180 }length 180 (user)length 180 (user): the user's choice stays

If you store values, both rows hold a plain number. You cannot tell which number to update.

Case 2. An option goes away and comes back. The user picks the extension b-50. Then the catalog drops b-50 for a time.

Output · picks { 'panel.length': 180, 'panel.extra': 'b-50' } stay the same
CatalogValue of panel.extraWhy
has b-50'b-50'the user's pick
has no b-50'none'a fallback; the engine reports that b-50 is not available
has b-50 again'b-50'the pick was never deleted

If you store values, row 2 writes 'none' over 'b-50', and the user's choice is lost. Step 6 explains the fallback.

Case 3. Save and check. The saved file holds only the picks, for example { "panel.length": 180, "panel.extra": "b-50" }. With each price request, the browser also sends the values that it showed (step 7). The server does not trust them. It computes every value again from the picks, with its own catalog, and compares. If a value is different, it rejects the order (step 8). So the picks are the input, and the values are only a record of what the user saw.

One more rule: in a change, null removes a pick. The field then goes back to its default, as if the user never touched it. Step 3 shows it.

Inside the engine: a handle carries a type that it does not hold

At run time a handle is { id, kind }. So how does TypeScript know that panel.length holds a number? TypeScript compares object types by their shape. Without help, a Field<number> and a Field<string> have the same shape and are the same type. The engine adds an optional property under a symbol that is only declared. The property has the value type in it. No object ever has this property, but the compiler sees it, and the two types become different.

packages/configurator/src/engine/fields.tslines 1–50, trimmed ↗
export type Json = string | number | boolean | null;
export type Intents = Readonly<Record<FieldId, Json>>;

declare const fieldTypes: unique symbol; // declared only; no value exists

export interface Field<T extends Json = Json, O extends Option = Option> {
    readonly id: FieldId;
    readonly kind: FieldKind;
    readonly [fieldTypes]?: { readonly value: T; readonly option: O }; // compile time only
}

export interface NumberField extends Field<number> {
    readonly kind: 'number';
}

export function numberField(id: FieldId): NumberField {
    return { id, kind: 'number' };
}
The effectchecked with tsc --strict
const net = derivedField<number>('panel.net');
const d: DerivedField<string> = net;
// error TS2322: Type 'DerivedField<number>' is not assignable to type 'DerivedField<string>'.

A value is only JSON: a string, a number, a boolean or null. No objects and no arrays. So a pick goes into a saved file as it is, and the engine compares two picks with ===.

The engine checks each pick before it runs a rule. A pick for a derived field, or for an id that the product does not have, throws:

packages/configurator/src/engine/resolve.tslines 335–343 ↗
export function writableFieldOf<C>(definition: BuiltDefinition<C>, id: FieldId): NumberFieldDef<C> | ChoiceFieldDef<C> {
    const def = definition.byId.get(id);

    if (def === undefined || def.kind === 'derived') {
        fail('INTENT_INVALID', `no writable field '${id}'`);
    }

    return def;
}
Output · real runs
pick { 'panel.net': 1 }throws INTENT_INVALID: no writable field 'panel.net'
read the field numberField('panel.lenght') from a resultthrows FIELD_UNKNOWN: panel.lenght

The second row is the one mistake a handle cannot catch at compile time: a typo in the id string itself. That is why you spell each id once, in the handle, and import the handle everywhere else.

Keep this

Refer to a field only by its handle. Store only the picks. Never store a value that the engine can compute from the picks.
